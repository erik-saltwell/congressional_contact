# Project context

## Overview

Congressional Contact is a web page that lets a person quickly look up their two U.S. senators and their U.S. House representative and save those officials' contact details to their phone.

**Problem.** It is hard for people to reach their representatives when they want to influence a vote. Nearly every senator and representative publishes phone numbers, plus web forms or email addresses. But finding them in the moment, during a busy day, is a barrier to making contact.

**Solution.** A page where a user can look up their officials and download their details as contacts, as quickly and easily as possible.

**Why it works.** Once the contacts are on the phone, leaving a quick message at an office when the user wants a vote to go a certain way takes far less effort.

## Design goals

**Primary goal.** The page succeeds if every visitor who is on a phone, knows what the site is, and wants their officials' contact cards leaves with those contacts on their phone. That is the whole measure of success.

The page should be as clear, simple, and easy to use as possible.

**Secondary goal (half as important as the primary).** People who want to copy the page and self-host it can do so as easily as possible.

Design notes for the web page belong in the root-level `design_notes/` directory.

## Settled decisions

- **Officials per visit:** normally three: the user's two senators and their one House representative. DC and territory residents get the officials who apply to them, such as a delegate or the resident commissioner. Three contacts are not assumed everywhere.
- **Primary user (P0):** someone who can recognize the name of their own House representative. Supporting people who cannot is a lower priority (P1), through a link to the official House lookup.
- **Which Congress:** show officials currently serving, including during an election transition. Switch to successors when they take office, and keep district boundaries aligned with the serving Congress. (Flows, 2026-11-05.)
- **Vacant seats:** identify a vacancy explicitly and offer cards for the officials still serving. Never fill a vacant seat with a previous member's details.
- **Card contents:** full detail wherever the data has it: phone numbers, web form, email, and office addresses. No fax numbers (owner, 2026-11-05). Each card carries only the DC office and the local office nearest the user's ZIP, and says nothing about the offices it leaves out (owner, 2026-11-06; see [vcard-office-selection.md](design_notes/vcard-office-selection.md)).
- **Delivery:** one vCard per official, built in the browser, with a save link next to each person, so saving the three takes three taps. The same flow is used on every phone. For a ZIP with several candidate representatives, show all of them, each with its own link, with no selection step needed first. (User decision 2026-11-05. The earlier single-click "save all three" goal was dropped because iPhone Safari imports only the first card of a multi-contact file.)
- **Success condition:** the contacts are actually saved in the phone's contacts app. A completed file download is acceptable if the platform cannot do better.
- **No ZIP in the URL** (owner, 2026-11-05): never put the ZIP in the query string, the hash or the page title, because the Jekyll page inherits the site's Google Analytics. There are no shareable ZIP-results links. "Copy link" shares the starting page or the help link. The page fires no analytics events of its own.
- **Self-hosting:** static files copied to any web host, with no backend, accounts, or API keys. Self-hosters get a standalone single HTML file. Its only external dependency is Google Fonts.
- **Outputs and build** (see [jekyll-integration.md](research/jekyll-integration.md)): one shared source builds two outputs.
  - A four-file Jekyll version for eriksaltwell.com: `congress.html`, `_data/congress.json`, `assets/js/congress.js` and `assets/css/congress.css`. A copy script puts them into the site checkout, and the menu entry is a one-time `_config.yml` edit.
  - The standalone single file.

  Two Python scripts do the work: a data script and a build script. Data is inlined in both outputs and never fetched at runtime.
- **Styling** (see [existing-site-design.md](design_notes/existing-site-design.md)):
  - Match the existing Beautiful Jekyll site wherever possible. Since the site recolour, the page follows the site's colours, not stock Bootstrap (owner, 2026-11-06):
    - buttons and links in the navbar highlight brown (`#804214`);
    - hovers in the copper (`#C57735`);
    - all headings in `--heading-col` (`#584F4E`);
    - no blue anywhere.
  - The owner recoloured the site on 2026-11-05: an off-white page, an orange navbar and footer, and a new `--heading-col`. The Jekyll page inherits these. The standalone file copies the site's current values, not the theme defaults. Bootstrap's colours are unchanged. See the update section in [existing-site-design.md](design_notes/existing-site-design.md).
  - One button style: Find and Save are both `btn btn-primary btn-lg` (48 px), and Start over is a text link (owner, 2026-11-06).
  - Names use the theme's heading styles.
  - No icons by default.
  - Every id and class gets a `cc-` prefix.
- **Data maintenance:**
  - The owner refreshes the data manually, including at each new Congress. No scheduled automation is required.
  - A "review congressional data" agent skill checks every official online on each full refresh. The owner approves corrections and the agent applies them.
  - The owner is the only maintainer and owns the supplemental form and email registry.
- **Release plan** (owner, 2026-11-05; see the [implementation plan](.work-items/implementation-plan/plan.md)):
  - The first public release is a minimal lookup-and-save page on eriksaltwell.com, launched before January on the 119th Congress.
  - The review skill and a full pre-launch data review gate that launch.
  - A full refresh for the 120th Congress follows after it is seated on 2027-01-03.
  - Help, sharing, reporting, the standalone file and self-hosting releases come later.
- **Verification:** no unit tests (see [workflow.md](.work-items/workflow.md)). Use script assertions, the pinned GitHub Pages Jekyll build, browser checks, and checks on both phones for changes to saving or navigation.

## Research findings

Detailed notes are in `research/`. Each entry says whether the user approved it or it is only a research finding.

### Matching users to officials

Notes: [official-matching.md](research/official-matching.md), [zip-district-mapping.md](research/zip-district-mapping.md).

- **Approved:** a ZIP-first flow. The user enters a ZIP, the page shows candidate House members and the corresponding senators, and the user saves the cards they want. The official House lookup opens in a new tab when the user is unsure, and an escape route remains for missing or unexpected matches. This replaces the earlier plan of picking a state and then a name.
- **Approved ZIP source:** the HUD-USPS ZIP-to-congressional-district crosswalk (type 5), acquired locally by a maintainer and published as static JSON. HUD access is a maintainer-side exception: the deployed page and its data need no credential.
- **Finding:** a ZIP can span several districts and even several states (for example 10003 is NY-10 and NY-12; 42223 spans KY and TN). Never pick a district by largest share. Keep every candidate and store the state on each candidate, so senators are resolved per candidate.
- **Finding:** the Census ZCTA mapping is only a shortlist and differs from the official House postal lookup (it missed TN-1 for 42223). It stays as comparison evidence, not the source.
- **Finding:** the HUD crosswalk omits PO-box-only ZIPs, so missing ZIPs must not be treated as invalid.
- **Finding:** district boundaries and the roster must describe the same Congress. The Census geocoder already returns 120th Congress districts while the serving roster is still the 119th. Mid-decade redistricting means the 120th changes boundaries as well as members.
- Address lookup via the Census geocoder is feasible but needs JSONP, has no CORS support, and sends the user's address to Census, so it is not planned.

### Contact data and freshness

Notes: [contact-data-source.md](research/contact-data-source.md), [data-design.md](research/data-design.md), with evidence in [contact-data-source-evidence.json](research/contact-data-source-evidence.json).

- **Approved:** maintained static JSON holding the officials and lookup indexes. VCFs are generated from it in the browser. No backend, account or API key for visitors.
- **Sources:** the community-maintained congress-legislators files (CC0) for rosters, Washington DC contact details and district offices, cross-checked against the official House Clerk and Senate rosters. A small supplemental registry adds verified legislative feedback-form URLs and any published public mailboxes.
- **Finding:** coverage for current members is good for phones and addresses, but weak for forms and email. Only 2 House members and 86 senators had a contact form in the bulk roster, and none had an email. Most House offices publish a web form rather than a mailbox, so do not invent email addresses and do not put a form URL in a vCard `EMAIL` field. Keep casework mailboxes labeled as casework.
- **Format:** final schema in [design_notes/data-schema.md](design_notes/data-schema.md). Officials are keyed by Bioguide ID; `states` lists senators; `houseSeats` maps seat keys such as `NY-12` to a member or `null` when vacant; `zipMatches` maps five-digit ZIP strings to seat keys. No floating-point numbers are allowed.
- **HUD findings** ([hud-crosswalk-findings.md](research/hud-crosswalk-findings.md)):
  - Use 2026 Q2, which has 119th districts, and always pin the quarter.
  - Take the state from the district code, not HUD's `state` field.
  - American Samoa and the Northern Mariana Islands are missing and need hand-maintained ZIPs.
  - Appointed senators serve past their recorded term-end date.
- **Freshness:** a downloaded VCF is a snapshot; later data updates do not change contacts already on a phone. Keep the last good data if an upstream download fails.
- **Credential:** the HUD token is stored locally in a Git-ignored `.env` file (template in `.env.example`) and is used only by the local data-generation tools. It must never appear in docs, logs, bundles or published JSON. Authenticated access works (2026-11-05).

### Multi-contact import

Notes: [multi-contact-import-findings.md](research/multi-contact-import-findings.md).

- **Decision:** one vCard per official (vCard 3.0, UTF-8, CRLF line endings), built in the browser as a blob, with a save link next to each person.
- **Android (Chrome 156, Android 10):** a multi-contact file imported all contacts by plain link, `download` link, blob and `data:` URL. A single-contact file imported one contact. The Web Share API failed with `NotAllowedError`; do not use it.
- **iPhone (Safari, iOS 18.7):** every route showed a single contact card with the first contact only (Test Senator One), with Add New Contact or share to Contacts. No "Add All" option appeared. This is why the single-click goal was dropped. Sharing via the Web Share API does open the share sheet on iPhone.
- The temporary `vcard-test` branch and its GitHub Pages site have been removed. The test files remain in [research/vcard-test/](research/vcard-test/).
